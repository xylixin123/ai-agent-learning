为了能够更好地实现ai回答的个性化与专业化，需要用户记忆与知识库来辅助回答。
1.用户记忆
首先放哪里
用户记忆分两部分，轨迹和用户长期记忆，用户长期记忆由agent调用工具维护

下面讲怎么存
用户记忆有四种存储格式：Simple Notes、Enhanced Notes、JSON Cards 和 Advanced JSON Cards 。
Simple Notes简单，容易检索。但是信息量少。
Enhanced Notes完整，但是包含太多重复信息。
JSON Cards，使用json格式，方便查找与修改，但是背景信息缺少。
Advanced JSON Cards补充了背景信息。
除了上述4种格式，还使用代码来存储用户记忆。通过代码来计算长对话信息中的统计与规则约束，来减少模型的处理，集中去处理语意理解。

最后讲存什么
用户记忆按照内容和使用方式分类：
- 情景记忆，保存具体事件。
- 语义记忆，保存事实。
- 程序记忆，保存流程。

怎么管理与压缩
通过访问次数、使用频率、使用时间等指标来评分筛选。
通过分类来管理。
从场景记忆来提取一般性规律。

2.构建共享知识库的核心技术--检索增强生成rag。
rag由知识库检索得到上下文,增强喂给llm,再由llm生成回答。

再rag之前先对文档分块，有两个约束，分块太长核心信息被稀释，分块太短导致信息缺失。实践中常见的是每块 256-1024 token、相邻块重叠 10%-20%
有三种分块方法：
固定大小分块
按文档的自然边界（章节标题、段落、句子）递归切分
计算相邻句子的嵌入相似度，在语义“断崖”处切分。

稠密嵌入
将分好块的段落映射到向量，再由余弦相似度来判断相关性，这样方便将用户的提问映射到向量去检索。
稠密嵌入在一词多义的情况下有缺陷，需要根据上下文去映射向量。

稀疏嵌入
从关键词到相关性评分。
词袋不表示顺序，没出现的词得0分，
块中词出现频率越高，得分递减。
不同块的大小不一样，块越长，词得分越少。
块当中重要的词得分越高。

混合检索
稠密嵌入懂语意但是可能漏关键词，稀疏嵌入精准匹配但是不懂同义词。
第一步，并行检索
第二步，按排名来打分得到候选池。
第三步，神经重排序来精确打分，重排序得到最终结果。

3.知识的组织与检索
把文档分块，会丢失知识的内在层次和跨文档关联。因此需要把知识组织起来。

首先是两种结构化索引技术（RAPTOR 和 GraphRAG），它们解决“如何组织知识”的问题。
结构化索引的思路是：索引之前先用 LLM 把知识整理一遍——归纳、抽象、建立关联。
RAPTOR将语义相似的文档分成一组，在把这一组的生成聚类摘要，在根据聚类摘要生成全局摘要。
GraphRAG 将文档知识的主要内容主语-关系-宾语提取出来，根据这些组建知识图谱。

用目录结构组织知识
核心设计是 L0/L1/L2 三层上下文按需加载。资源写入时，系统自动将原始内容提炼为三个抽象层次：L0（摘要）约 100 tokens 的一句话概述，用于快速判断目录相关性；L1（概览）约 2,000 tokens 的核心信息与使用场景，供 Agent 规划决策；L2（全文）为完整原始内容，仅在需要深入时按需加载。每个目录下自动生成 .abstract（L0）和 .overview（L1）文件，形成从根到叶的层次化摘要结构。若在 L0 层即判定无关，则无需加载 L1 和 L2——大部分查询加载到 L1 即可完成决策，Token 消耗因此大幅降低。
文件的格式使用Markdown 纯文本，方便人查看。
文件之间必须建立起链接与索引，方便模型检索。

4知识的更新
但一个上线运行的用户记忆或共享知识库还会持续收到新信息。只更新不整理，内容会越积越乱；只做定期重写，新信息又无法及时生效。因此，完整的更新机制必须同时包含两条路径：事件触发的增量更新，以及周期触发的全量整理

增量更新：
1. 提议者—审核者模式，把知识更新做成一个有外部证据的迭代闭环：
Proposer Agent 提交 PR。它从原始证据中发现新事实、冲突或过期内容，在工作分支上提出尽可能小而完整的 diff。它不是把最新一次对话粗暴追加到文件末尾，而是先检索相关的已有知识，再增、删、改对应条目，同步维护链接、索引、时间元数据和证据引用。
2. Reviewer Agent 独立审核。它拿到变更前的知识、diff 和原始证据（如 execution，trajectory、原始对话、业务文档或工具执行结果），独立检查每个新断言是否能被证据支持、是否漏限定条件、是否与其他文件冲突，以及删除或改写是否过度。审核不通过时，它应返回指向具体证据和行号的可执行意见，而不是模糊地说“还需要改进”。
3. 双方迭代至收敛。 Proposer 根据拒绝理由修改 diff，Reviewer 再次回到原始证据复核；只有 Reviewer 明确批准，PR 才可合入。同时要设置最大迭代次数或成本预算；超出上限仍未收敛时转人工审核，不能默认放行。
4. 合入后再发布。 CI 先检查格式、链接、元数据、权限标签；若知识以代码表示，还要运行类型检查和测试。通过后才从已合入的版本增量重建受影响的分块、摘要和向量索引。因此，索引是可重建的派生物，Git 中已审核的知识才是真正的来源。

全量整理：
1. 去重、去旧与合并。
2. 回到原始数据核查。
3. 冲突解决与场景限定。

5.智能体化 RAG
为 Agent 构建了强大的知识库之后，下一个核心问题是：Agent 如何才能智能地、自主地利用这个知识库？
传统的 RAG 流程通常是一个简单直接的单向数据流：用户的查询直接用于检索，检索结果直接注入模型上下文，模型直接生成最终答案。
简单问题的检索够用，但是当问题复杂时，检索的结果就可能不准确。
智能体化 RAG在调用检索工具之后，先判断结果够不够用，够用就直接生成答案，不够用就调用工具继续检索。

6.RAG 技巧：上下文感知检索
智能体化 RAG 框架仍有缺陷，文档分块会对背景知识造成损失，导致信息不够准确。
核心思想非常直观：在对文本块进行向量化索引之前，先利用 LLM 为其生成一段简短的、包含核心上下文的“前缀摘要”，然后将前缀与原始文本块拼接后再索引。

7.从数据集中提取深度知识：从信息检索到知识发现
RAG 技术都基于一个前提：知识以非结构化或半结构化的文档形式存在。然而在许多专业领域，知识更多以隐性、分散的形式蕴含在海量结构化案例数据中。
过程分两阶段：
第一阶段：知识提取与结构化。利用 LLM 强大的理解和归纳能力，将每个案例的非结构化描述转换为包含所有关键判决因素的标准化 JSON 对象。
第二阶段：在获得大规模结构化数据后，运用数据分析技术发现模式、提炼规律，识别出哪些因素对最终结果具有最显著影响并量化其权重，构建“判决因子重要性层次模型”——这就是从海量案例中提炼出的可供 Agent 使用的“判决经验”。
